## Dataset Purpose

This dataset is used to validate the first AEGIS-HGX machine learning platform mechanics.

It supports:

- synthetic event generation
- baseline model training
- data generation tests
- model shape tests
- inference API contract tests
- CI reproducibility checks
- model card and data card documentation

This dataset is not intended to prove real-world cyber threat detection quality.

## Current Pipeline Position

```text
synthetic event generator
→ synthetic tabular dataset
→ baseline logistic regression model
→ model artifact
→ FastAPI inference endpoint
→ tests and CI
```

## Label Definitions

| Label | Meaning |
|---|---|
| `0` | Synthetic normal event |
| `1` | Synthetic suspicious event |

The labels are generated by the synthetic data generator.

They represent generator-defined suspiciousness, not verified real-world attack labels.

## Intended Use

This dataset is intended for:

- validating the synthetic data generation pipeline
- training the initial baseline logistic regression model
- testing model input shape contracts
- testing inference API request and response contracts
- validating CI reproducibility
- supporting local engineering demonstrations
- supporting early MLOps platform development
- documenting baseline dataset assumptions

This dataset may be used for controlled local experimentation and portfolio demonstration.

## Out-of-Scope Use

This dataset is not intended for:

- real-world cyber threat detection claims
- production SOC monitoring
- customer-facing security decisions
- autonomous blocking or containment decisions
- legal, compliance, or employment decisions
- benchmarking against real IDS datasets
- claims of adversarial robustness
- claims of temporal anomaly detection quality
- claims of graph anomaly detection quality

The dataset is synthetic and should not be treated as representative of real enterprise security telemetry.

## Dataset Assumptions

The current dataset assumes:

- each row represents one independent synthetic cyber event
- labels are binary: `0 = normal`, `1 = suspicious`
- the configured anomaly rate controls the approximate suspicious-event share
- normal and suspicious behavior can be separated using the current feature set
- suspicious patterns are generated from predefined synthetic rules
- categorical values such as users, hosts, processes, and IPs come from synthetic pools
- event timestamps are generated from configured normal and suspicious hour ranges
- inference payloads follow the same schema as the training dataset

## Known Limitations

The current dataset has the following limitations:

- no real endpoint, network, authentication, DNS, firewall, or EDR telemetry
- no public IDS dataset coverage yet
- no real attacker behavior
- no real benign enterprise behavior
- no analyst-verified labels
- no temporal sequences beyond individual event timestamps
- no graph structure connecting users, hosts, processes, and network entities
- no multi-stage attack chains
- no user behavior history
- no host behavior history
- no adversarial examples
- no real production drift measurement

## Bias and Imbalance Risks

The synthetic generator may encode artificial shortcuts.

Examples:

- suspicious events may be too strongly associated with high `bytes_out`
- suspicious events may be too strongly associated with off-hours activity
- suspicious events may be too strongly associated with specific process names
- normal events may be too clean or too predictable
- categorical values may be easier to separate than real enterprise telemetry

These biases can cause the model to learn generator-specific patterns instead of general cyber anomaly behavior.

## Leakage Risks

Potential leakage risks include:

- labels may be too directly tied to generator rules
- suspicious process names may reveal the label too easily
- suspicious hours may reveal the label too easily
- byte-count ranges may reveal the label too easily
- train/test splits may share the same synthetic generation process

These risks are acceptable for early platform validation but must be reduced before making real detection claims.

## Data Quality Checks

Current data-generation tests verify:

- configured row count is produced
- required columns are present
- labels are binary
- both normal and suspicious examples are present
- event hours are between `0` and `23`
- business-hour flags are valid boolean-compatible values
- byte counts are non-negative
- generated output is reproducible for the same seed
- generated CSV can be saved and reloaded
- configured anomaly rate is reflected in the label distribution
- invalid generation config values are rejected

## Required Future Validation

Before this dataset can support stronger cyber-detection claims, AEGIS-HGX should add:

- public IDS dataset ingestion
- real network-flow feature mapping
- label-quality analysis
- class-imbalance analysis on real data
- temporal train/validation/test splitting
- leakage audit
- graph construction from users, hosts, processes, and network entities
- data drift reports
- feature distribution comparison between synthetic and public data
- false-positive and false-negative case studies
- adversarial or evasive-behavior examples
